## 1. Концепция проекта

Ascend — локальная система персонального фитнес-тренера, которая превращает регулярные тренировки, физическую активность и контроль состояния организма в RPG-систему.

Система собирает данные о физической активности и состоянии пользователя, анализирует их, определяет текущую готовность к нагрузке и формирует персональные задания (квесты).

**Основная идея:**

```
Физическая активность
        +
Биометрические данные
        +
История тренировок
        +
Калибровка пользователя
        ↓
   Readiness Engine
        ↓
  Quest Generator
        ↓
   Ежедневные квесты
        ↓
       EXP
        ↓
   Уровни и характеристики
        ↓
       Боссы
        ↓
    Прогресс пользователя
```

> Проект не является медицинской системой и не предназначен для диагностики заболеваний. Показатели состояния используются исключительно для адаптации тренировочной нагрузки.

---

## 2. Основные цели

Система должна позволять пользователю:

- пройти первичную физическую калибровку;
- получать персональные ежедневные квесты;
- выполнять и фиксировать квесты;
- автоматически импортировать данные из Apple Health;
- вручную добавлять данные;
- хранить исходные данные импортов;
- повторно интерпретировать ранее импортированные данные;
- рассчитывать уровень готовности к нагрузке;
- адаптировать сложность тренировок;
- получать опыт;
- повышать уровень;
- развивать игровые характеристики;
- выполнять долгосрочные цели («боссы»);
- получать достижения;
- получать случайные игровые награды;
- отслеживать статистику и прогресс;
- взаимодействовать с системой через Telegram;
- экспортировать собственные данные.

## 3. Основные архитектурные принципы

### 3.1. Local-first

Все основные данные хранятся локально.

Ascend не требует постоянного подключения к облачному серверу для основной работы приложения.

```
Desktop Client
      │
      ▼
 Local FastAPI
      │
      ▼
    SQLite
```

Telegram является дополнительным каналом взаимодействия и не заменяет локальный клиент.

### 3.2. Разделение исходных и обработанных данных

Исходные данные никогда не должны зависеть от текущей логики интерпретации.

Используется принцип:

```
Raw Data
   ↓
Interpreter
   ↓
Normalized Data
   ↓
Derived Data
   ↓
Game Logic
```

Это позволяет изменять алгоритмы обработки без потери исходных данных.

### 3.3. Независимость источников

Бизнес-логика Ascend не должна зависеть от конкретного поставщика данных.

Например:

```
Apple Health ──┐
               │
CSV ───────────┼──→ Interpreter → health_metrics
               │
Manual ────────┘
```

В будущем могут быть добавлены:

- Google Fit;
- Garmin;
- Strava;
- другие фитнес-платформы.

Quest Engine и Readiness Engine при этом не должны требовать изменения при добавлении нового источника.

## 7. HealthSync

### 7.1. Назначение

HealthSync отвечает за получение, хранение и интерпретацию внешних данных.

HealthSync разделяется на:

1. Raw Storage;
2. Data Interpreter;
3. Normalizer;
4. Validation;
5. Metrics Storage.

### 7.2. Источники данных

Основным внешним источником является: **Apple Health**.

Поддерживаются:

- официальный экспорт Apple Health;
- XML;
- JSON при наличии поддерживаемого формата;
- CSV/JSON структурированный импорт;
- ручной ввод.

> В MVP-прототипах и локальной версии автоматическая синхронизация не является обязательной.

## 8. Raw Storage

### 8.1. Принцип

При импорте исходные данные сохраняются без изменения.

Например:

```
Apple Health Export
        ↓
raw_health_imports
        ↓
Data Interpreter
```

Raw-данные не должны изменяться при последующей обработке.

### 8.2. Таблица `raw_health_imports`

| Поле          | Тип    | Описание                              |
|---------------|--------|---------------------------------------|
| `id`          | INT    | Первичный ключ                        |
| `user_id`     | INT    | Внешний ключ на пользователей          |
| `source`      | TEXT   | Источник данных                       |
| `file_name`   | TEXT   | Имя файла                             |
| `file_hash`   | TEXT   | SHA-256 хэш файла                     |
| `format`      | TEXT   | Формат файла                          |
| `raw_data`    | TEXT   | Сырые данные                          |
| `imported_at` | DATETIME | Время импорта                       |
| `status`      | TEXT   | Статус обработки                      |

`file_hash` используется для определения повторного импорта одного и того же файла.

### 8.3. Идемпотентность

Повторная загрузка одинакового файла не должна создавать дубликаты.

```
export.xml
   ↓
SHA-256
   ↓
file_hash
   ↓
уже существует?
   ├── Да → не импортировать повторно
   └── Нет → создать Raw Import
```

## 9. Data Interpreter

### 9.1. Назначение

Interpreter преобразует внешние данные в внутренний формат Ascend.

Пример:

```
HKQuantityTypeIdentifierBodyMass
            ↓
          weight
            ↓
          kg
```

### 9.2. Поддерживаемые метрики

Минимальный набор:

| Apple Health             | Ascend        |
|--------------------------|---------------|
| `BodyMass`               | `weight`      |
| `BodyFatPercentage`      | `body_fat`    |
| `RestingHeartRate`       | `resting_hr`  |
| `ActiveEnergyBurned`     | `active_energy` |
| `StepCount`              | `steps`       |
| `DistanceWalkingRunning` | `distance`    |
| `SleepAnalysis`          | `sleep`       |
| `VO2Max`                 | `vo2max`      |

В будущем список может расширяться без изменения архитектуры.

---

## 10. Нормализация данных

Interpreter должен приводить данные к внутренним единицам Ascend.

Пример:

```
lb  → kg
mile → km
minute → hours
```

Для каждой метрики определяется базовая единица.

Например:

| Metric          | Base Unit   |
|-----------------|-------------|
| `weight`        | kg          |
| `body_fat`      | %           |
| `resting_hr`    | bpm         |
| `sleep`         | hours       |
| `steps`         | steps       |
| `distance`      | km          |
| `active_energy` | kcal        |
| `vo2max`        | ml/kg/min   |

## 13. Интервальные данные

Некоторые источники, например данные сна, представлены интервалами.

Interpreter должен уметь:

- определять начало;
- определять конец;
- учитывать пересечения;
- объединять перекрывающиеся интервалы;
- агрегировать интервальные данные в суточные показатели.

Пример:

```
00:00 ───────── 07:30
        Sleep
        ↓
sleep = 7.5 hours
```

> Двойной подсчёт перекрывающихся интервалов не допускается.

---

## 14. Обработка отсутствующих данных

Отсутствие данных не считается ошибкой.

Например:

```
VO2max отсутствует
        ↓
не создавать фиктивную запись
        ↓
Readiness Engine работает без VO2max
```

Ошибки парсинга записываются в `sync_logs`.

> Ascend не должен прекращать работу из-за отсутствия отдельной метрики.

## 15. Перепроцессинг

Пользователь или backend может повторно обработать существующий Raw Import.

```
Raw Import
    ↓
Interpreter v1
    ↓
Metrics
Interpreter v2
    ↓
Metrics обновляются
```

Это позволяет менять алгоритмы интерпретации без повторной загрузки исходного файла.

## 16. Readiness Engine

### 16.1. Назначение

Readiness Engine определяет, насколько пользователь готов к запланированной нагрузке.

**Результат:** `0–100`

| Диапазон | Уровень готовности     |
|----------|------------------------|
| 0–20     | критически низкая      |
| 21–40    | низкая                 |
| 41–60    | средняя                |
| 61–80    | хорошая                |
| 81–100   | высокая                |

> Границы должны быть конфигурируемыми.

---

## 17. Факторы Readiness

Используются:

- сон;
- пульс покоя;
- активность;
- недавняя тренировочная нагрузка;
- история выполнения;
- субъективная оценка состояния;
- при наличии — VO₂max;
- длительность восстановления после тяжёлых тренировок.

Каждый фактор имеет собственный вес.

---

## 18. Readiness Score

Условная структура:

```
Readiness
    =
    Sleep Score
    +
    Resting HR Score
    +
    Training Load Score
    +
    Recovery Score
    +
    Activity Score
```

Конкретные коэффициенты должны храниться в конфигурации, а не быть жёстко зашиты в Quest Engine.

---

## 22. Адаптивная сложность

Каждый квест имеет базовую сложность.

Например:

```
Calibration maximum = 30 push-ups
Difficulty coefficient = 0.6
Quest = 18 push-ups
```

Коэффициент зависит от:

- Readiness;
- уровня;
- недельного прогресса;
- тренировочной нагрузки;
- истории выполнения.

---

## 23. Безопасное снижение нагрузки

При низком Readiness:

```
Readiness ↓
      ↓
Difficulty Modifier ↓
      ↓
Quest Volume ↓
```

Например:

```
плохой сон
+
повышенный resting HR
        ↓
Readiness = 42
        ↓
снижение тренировочного объёма
```

> Система не должна самостоятельно выдавать экстремальную нагрузку.

## 28. Опыт

## 29. Система уровней

Каждый следующий уровень требует больше опыта.

**Базовая модель:**

```
EXP_next = EXP_base × 1.2^(level - 1)
```

> Точные значения должны быть вынесены в конфигурацию.

## 56. Безопасность

Даже локальное приложение должно:

- не хранить пароль в открытом виде;

## 77. Главный принцип проекта

Ascend должен строиться не вокруг конкретного источника данных, конкретного интерфейса или конкретного алгоритма генерации квестов.

**Основой является универсальная цепочка:**

```
DATA
 ↓
INTERPRETATION
 ↓
STATE
 ↓
DECISION
 ↓
ACTION
 ↓
PROGRESS
```

Это позволяет системе постепенно расширяться без переписывания ядра проекта.

> **Итоговая цель:** создать полноценную локальную RPG-систему тренировок, в которой реальные данные пользователя влияют на игровую систему, а игровая система мотивирует пользователя поддерживать регулярную физическую активность.
